# rust/ - Rust and JS-Rust Boundary Rules

## Workspace Layout

- Real logic lives in `parse_ast` (AST conversion) and `xxhash`; `bindings_napi` and `bindings_wasm` are thin shims — new parsing/conversion code goes into `parse_ast`, never into a binding
- `build:wasm` targets the web (output `wasm/`, used by the browser) and `build:wasm:node` targets nodejs (output `wasm-node/`); both build the same `bindings_wasm` crate, so changes affect browser and Node-WASM alike
- The toolchain is pinned in `rust-toolchain.toml`; use the npm build scripts, not bare cargo. `lint:rust` (cargo fmt + clippy) is not run by the pre-commit hook — run it manually

## Codegen Contract

- `scripts/ast-types.ts` is the single source of truth for the buffer layout. `npm run build:ast-converters` regenerates the Rust constant/macro files AND the JS parsers; the only schema outside `ast-types.ts` is the fixed string table in `scripts/string-constants.ts`, which the same command regenerates
- Node-type codes are positional: inserting or reordering a node in `AST_NODES` renumbers all later type codes on both the Rust and JS side
- In `ast-types.ts`, `hasSameFieldsAs`, `useMacro: false` and `fixed` are codegen directives, not dead config: they control whether a node reuses another node's field constants, is implemented as a manual `store_*` function in `ast_nodes/` instead of a generated macro, or has a constant field. Check these before assuming all nodes are macro-generated
- The SWC parser runs with a fixed `EsSyntax` feature set in `parse_ast/src/lib.rs` — supporting a new JS syntax feature means enabling it there and handling the new AST variants in the converter, not per-binding

## Buffer Format

- The AST buffer is 4-byte aligned throughout and every 32-bit word is a native-endian u32 (written with `to_ne_bytes()`); strings are packed LSB-first into native u32 words (first string byte into the lowest byte position) with a native `u32` byte-length prefix, f64 values are a pair of native u32 words (low bits first), and the buffer sections are plain u32 words appended after conversion — new fields must keep every word a native u32 and preserve alignment
- Every buffer starts with the buffer inventory declared in `BUFFER_INVENTORY_FIELDS` in `scripts/ast-types.ts`, generated into `converter/buffer_inventory_constants.rs` (byte offsets) and `src/utils/bufferInventory.ts` (word indices and readers): the `formatVersion` word, a word reference to the AST root followed by one word per section, where a section reference points at `[word count][words...]` and a field declared with `allowNull` is encoded as a 0 reference and decoded as null when its section was not collected. A new section is appended length-prefixed and gets its own inventory field, declared with `allowNull` unless it is always written; never reuse or reinterpret a slot
- Increase `BUFFER_FORMAT_VERSION` in `scripts/ast-types.ts` when a pull request changes the buffer layout, at most once per pull request. `scripts/buffer-format.json` records the version and a single fingerprint hashing all declarative layout data at once — `astNodeNamesWithFieldOrder`, `BUFFER_INVENTORY_FIELDS`, the `buffer-layout.ts` constants and `firstFieldWordOffset` values, `SCOPE_NODE_FIELDS` and `STRING_CONSTANTS` — so data dropped from these sources changes it as well; `npm run build:ast-converters` rewrites that file and fails once when the fingerprint changed, so the update has to be committed. CI compares the file against the base commit and fails if it changed without a higher version, and `getAstBuffer` rejects buffers with a foreign version. Changes the fingerprint cannot see — `converter.rs`, `annotations.rs`, `utf16_positions.rs`, `ast_nodes/**`, `lib.rs`, `src/utils/getAstBuffer.ts`, the templates in `scripts/generate-ast-to-buffer.ts`, `generate-rust-constants.ts` and `generate-buffer-to-ast.ts`, `scripts/generate-buffer-inventory.ts` (section encoding, the `0` null sentinel and the generated readers), `scripts/generate-string-constants.ts` (packed-word string encoding) and `scripts/buffer-format.ts` itself — need the same manual bump and have to be caught in review
- Big-endian hosts are handled on the JS side: the WASM wrappers (`native.wasm.js`, `browser/src/wasm.ts`) flip the whole buffer once after `parse` and `parseAndWalkSync` — never in `getAstBuffer`, which cached buffers re-enter through (double-swap hazard); the JS string/float decode helpers and the JS serializer are the only endian-aware JS code, and the WASM bitset is read by value so its u64 words are host-independent
- Build one `Vec<u8>` strictly forward; reserve header/child slots up front (`add_type_and_start` + `resize`) and patch references via `update_reference_position` (references are 32-bit word indices into the buffer, 0 means absent) — never re-index or walk the buffer to fix offsets; `shrink_to_fit` only at the end
- Every node starts with the header `[type][encoded parent][start][end]`. Nodes whose schema declares flags have one flags word after `end`, so the first field is at `type_position + 4`, or `+ 5` with flags (`getFirstFieldWordOffset` in `scripts/buffer-layout.ts`). The encoded parent is the parent node's type-word index plus one; 0 means no parent (the AST root, which directly follows the buffer inventory, and the `ParseError`/`PanicError` nodes). `add_type_and_parent` derives it from `node_position_stack` and `add_end` pops that stack, so node starts and ends must stay balanced — the only nodes converted before their real parent is known are decorators stored outside the class span, which `reparent_decorators` fixes once the class header exists
- `parse_ast` never returns `Result`: parse errors are always encoded as a `ParseError` AST node that JS detects and converts to a thrown error; on NAPI, panics are caught and encoded as `PanicError` the same way, but the WASM build uses `panic=immediate-abort` and simply aborts — keep these protocols
- Positions are normally emitted in ascending order. The only exceptions are nodes that reuse the range of an earlier sibling — the key of a shorthand property and the name of an unaliased import or export specifier — plus, for `{ a = 1 }`, the `AssignmentPattern` and its left side, which both start at the key. The UTF-8→UTF-16 converter derives such an index by subtracting the UTF-16 length of the text between their position and the cursor, and such nodes must not collect annotations. Any other backwards position is a bug, which debug builds assert by requiring it to stay at or after the start of the last advance. Stored `start`/`end` are UTF-16 code-unit offsets, never raw SWC UTF-8 spans

## Bindings Sync

- A new binding function must be added to both `rust/bindings_napi/src/lib.rs` AND `rust/bindings_wasm/src/lib.rs` plus all three JS handover points with matching names: `native.js`, `native.wasm.js`, `browser/src/wasm.ts` (`lint:native-js` only checks that every export in `native.js` is also present in `native.wasm.js` — signatures and reverse parity are not checked)
- napi-rs auto-camelCases Rust names; wasm-bindgen needs an explicit `#[wasm_bindgen(js_name = ...)]` where the camelCase mapping is not automatic
- Build-flag-gated bindings (NAPI only, e.g. `flush_llvm_coverage`) need a conditional export in `native.js` AND a no-op in `native.wasm.js` to keep the export-parity lint green
- `native.d.ts` and `wasm/*.d.ts` are auto-generated — never hand-edit them
